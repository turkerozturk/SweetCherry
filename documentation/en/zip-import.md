# Import folders and files from ZIP

Select a writable database and sign in as an administrator. Open **Import folders and files from ZIP** from the navigation menu.

1. Select a ZIP file. Its compressed size must fit `spring.servlet.multipart.max-file-size`, with an additional hard maximum of 256 MB. `spring.servlet.multipart.max-request-size` also applies to the whole upload request, including form overhead.
2. Choose whether to remove the last extension from file node names, import binary files as attachments, and create information-only nodes for oversized files. Choose the text encoding; UTF-8 is the default. UTF-8/UTF-16 byte order marks are detected automatically. Other offered encodings cover common Windows Western European and Turkish text files.
3. Review the counts and first 200 paths, resulting names, actions, syntax and sizes. Nothing is written during preview. To change the options, cancel and upload again.
4. Confirm within ten minutes. The ZIP's top-level entries are appended, in archive order, after the database's existing roots. Missing parent directories are created automatically, including empty folders. Refresh the database tree to see the result.

Folders use `plain-text` and `CT_DIRECTORY`. Recognized text files use the canonical `CodeIcon.fileExtension` mapping and its syntax/icon: for example, `.md` → `markdown`, `.py` → `python`, `.html` → `html`, `.java` → `java`. Extensions are case-insensitive; aliases include `.htm`, `.yml`, `.cmd` and common C/C++ extensions. Variant syntaxes such as `markdown-extra` and `python3` remain available in Node Properties but do not compete for `.md` or `.py`. Other text files use `plain-text` and `CT_NOTES`.

Binary detection uses common signatures/extensions, strict decoding and control-character checks. Choose the correct encoding for legacy text; detection cannot identify every possible file format or encoding. Binary files within the selected database's `custom.maxEmbeddedFileSizeMB` limit can become rich-text nodes with `CT_FILE` and one downloadable attachment. The original attachment filename is retained even when the node name omits its extension. ZIPs inside the archive remain ordinary attachments, not recursively imported archives.

Text files larger than 2,000,000 bytes and binary files above the attachment limit can become `plain-text` information nodes with `CT_CANCEL`. These always retain the full filename and include the ZIP path, declared byte size and available creation/modification/access timestamps in UTC, formatted as `yyyy-MM-dd HH:mm:ss`. Missing archive dates are explicitly marked unavailable; node-property dates use the import time when a source date is absent. Oversized entries are not decompressed and their metadata is taken from the ZIP directory. Disable this option to skip these files. Disable binary attachments to skip binary files that fit the attachment limit.

Imports are limited to 10,000 ZIP entries/resulting nodes, 64 path levels, 64 MB of total decompressed file data read, and 32 MB of retained text/attachment content. These limits apply in addition to upload and per-attachment settings. Stored/Deflate ZIPs with UTF-8 member names are supported; encrypted archives are not. Invalid paths, duplicate entries, file/folder collisions, parent traversal and absolute paths are rejected. No member is extracted to the server filesystem, and links/scripts/programs are not executed. Read file contents are size- and CRC-checked.

The preview belongs to the current database and browser session and can be confirmed once. Switching databases, expired or reused previews and read-only settings prevent confirmation. New node IDs are allocated; names can coincide with existing nodes without replacing them. All node, hierarchy and attachment inserts use one transaction. An insert failure rolls the complete import back. Text sources are preserved apart from decoding and removal of a byte order mark. This file-based import does not restore CTB IDs, bookmarks or source-node properties from a previous export.
